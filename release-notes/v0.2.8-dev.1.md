# 0.2.8-dev.1 — 门控循环与多轮历史（开发版）

本版本在 `dev` 开发，未提升到 `main`。稳定安装仍使用 `github:yogurtss/dsh-teamflow#main`；体验本功能使用 `github:yogurtss/dsh-teamflow#dev`。

## 使用方式

1. 配置执行成员与任务，连接普通前向依赖，在末端添加检查节点。循环内每个任务必须指定成员。
2. 选择检查节点，在「门控循环」中选择上游入口。逐环选择人工或 AI；AI 必须指定不同于环内执行者的审核成员。
3. 配置轮次上限（默认 3，包含首次执行）和超时（默认 30 分钟）。待启动流程点击启动；已经运行的流程可点「开始全部」或「启动循环」。外部输入未完成时排队等待。
4. 人工审核先读取本轮材料，填写审核意见、修改要求、复验条件，并选择要改进的任务。AI 通过专用审核工具提交同样的决定。
5. 「通过」放行下游；「改进」重跑所选原节点及其受影响下游；「无法继续」暂停。达到轮次上限不会自动通过，必须人工追加有限轮数或结束循环。
6. 在任一环内节点点击「查看多轮历史」：分页查看执行结果、任务要求、验证记录、审核意见、成员与模型，固定记录后可翻页比较。复用结果标明来源轮次。归档及恢复保留历史。

门控在画布中显示为菱形判断卡片：人工审核使用琥珀色，AI 自动审核使用紫色；名称、状态和轮次清晰区分。前向连线接左右顶点，循环退回线从底部引出。

循环布局按整个循环体排列，保留多个执行步骤和并行汇合；门控单独错行，浅色区域标出循环范围。绿色实线 **PASS** 指向环外任务，紫色虚线 **REJECT** 带箭头返回循环入口。模板卡片和详情也显示两条路径；详情可切换「循环路径／完整流程」。工作台「自动整理」识别循环，已有保存布局可用此操作重新排布。这里只调整显示，回退线不会写入普通依赖。

循环按任务需要选择，并非默认流程。一次性工作保持普通 DAG；同一个 workflow 可以混合普通任务、人工门控循环和 AI 审核循环。模型直接建队的 `plan.tasks[].checkpoint` 与可选 `plan.loops` 支持原子创建完整方案；循环引用本次 plan 的局部任务 ID，由服务端转换为持久 ID。未提供循环上限时默认 3 轮、执行超时默认 30 分钟；用户有明确要求时按要求生成。规划阶段仍等待用户确认，不自动执行。

## 调度与保存

内置模板库新增两个可选循环模板：

- **算子持续优化循环**：规格与目标 → 人工确认 → 固定基线 →〔优化实现 → 独立正确性验证 → 性能评测 → AI 门控〕→ 汇总交付。默认 5 轮，执行和 AI 审核阶段各 60 分钟超时。输入包括实际设备、精度容差、用例矩阵、测量协议与性能目标；门控只在全部达标时放行，平台期或外部阻塞应暂停。连续两轮无有效进展的判断由 AI 审核执行，硬轮次上限由系统保证。
- **修复与回归验证循环**：复现与根因 → 人工确认范围 →〔修复 → 独立回归 → AI 门控〕→ 汇总交付。默认 3 轮，执行和 AI 审核阶段各 60 分钟超时。打回保留问题定位、证据、修改要求与复验条件，不通过删除测试或放宽标准“修好”问题。

两者均保留一次性的准备和交付节点，使用时结合用户目标生成完整任务要求；不替代既有普通流程模板。模板包含中英文内容，复制到个人库后独立保存。AI 审核员不承担环内实现、验证或测量任务。

- 回退边单独保存，普通任务依赖仍是 DAG。每轮复用节点 ID，不生成 repair/review 新节点。
- 失败任务及被其阻塞的后续任务仍可进入门控，不能因等待失败依赖而永久停在执行阶段；未完成必需任务或失败验证不能通过。
- 每环单次运行最多 20 轮，包含人工追加；每环最多 32 个执行节点。首版支持互不重叠的单入口、单门控区域，禁止嵌套、共享节点、绕过门控的环外输出和普通依赖环。
- 执行阶段及 AI 审核阶段分别受所配超时约束，15 秒巡检；人工等待不计审核超时。派发失败、执行会话中断、材料漂移或用户暂停阻止自动推进。恢复必须显式操作，不无限自动重试。
- 决策绑定运行 ID、轮次、材料指纹；AI 还绑定审核者及执行令牌。重复决策不重复开轮，旧令牌不能完成新一轮，普通任务工具不能直接完成门控。
- 历史以不可变记录写入团队目录的 `loop-history/`，先保存历史，再以版本比较和原子替换提交当前清单。跨进程写入锁阻止同时提交；历史写入失败不会发布新轮次。死进程锁可恢复，不完整锁会明确报错并停止写入。
- 常规状态响应只携带当前结果和历史索引；历史每页最多 5 条。历史不触发模型调用。审核文件摘要在后台线程计算并有超时，避免大文件阻塞宿主事件循环。

## 默认质量策略与首版边界

新建空白流程、直接创建的团队及新模板实例默认关闭旧式隐式质量评审和自动扩图返工。显式配置的审核、验证、权限与证据检查继续生效；选择本身含评审节点的模板仍会运行这些节点。已有旧团队和明确使用旧 profile 的流程保留原策略；环内始终禁止旧式自动扩图。

启动后固定环内任务契约、负责人及外部输入。已通过循环不支持原地开启全新运行；需要修改结构、外部输入或重新执行整环时，保存为模板并新建流程。配置创建后也不提供原地拆环/改模式入口。这样保留原运行及其决定的含义。

审核意见目前保存为一段完整文本和返工任务列表，不提供逐条 finding 的独立状态管理。历史保存任务与证据快照、材料指纹，不复制工作区文件、不会恢复旧文件内容；模板只携带结构与循环配置，不携带执行历史。不存在旧版本降级迁移承诺。

## 验证证据

- 后端与前端 TypeScript 编译、客户端构建和 Git 安装产物一致性检查。
- 仓库完整验证链 36 个命令全部通过，其中包含 522 个 Node 测试用例；循环专项 19 项，含 50 个固定种子随机 DAG、同节点三轮改进、部分重跑、失败汇合、上限、超时、权限/旧令牌/重复提交、文件漂移、模板、归档恢复、陈旧写入者和部分历史写入故障。
- 20 轮样本产生 61 条历史：当前状态约 63.7 KB，与首次结果约 63.7 KB 持平；本机一次运行写入约 232 ms，遍历分页历史约 42 ms。该数据是本机小样本，不能视作大型项目性能承诺。
- Edge 无头浏览器：实际 React 工作台、HTTP 路由、保存与调度，人工/AI 两条三轮流程、达到上限、追加轮数、下游交付、历史分页/比较、不随轮询拉取历史、600 px 窄屏、深色主题、无页面异常和横向溢出。仅执行者/模型响应由样本模拟。
- 打包产物在隔离的真实 Harness `0.2.1-rc.5` Loader、HTTP 身份认证、调度器和成员工具上执行人工/AI 三轮场景；规范化结果见 `scripts/fixtures/gated-loops.snapshot.json`，覆盖冷启动后的历史保留。
- 未验证真实供应商模型的审核质量、其他操作系统、所有支持的宿主版本，以及真实用户数据的降级迁移。未发布 npm、未修改稳定分支。

浏览器复验：先运行 `node scripts/loop-preview.mjs`，再运行 `node scripts/loop-browser.mjs`；人工模式设置 `TEAMFLOW_LOOP_MODE=human` 并使用新启动的预览样本。可用 `TEAMFLOW_PLAYWRIGHT_MODULE` 指定现有 Playwright 模块。预览仅监听本机，状态和截图位于未入库的 `output/`。

## 2026-11-09 整体执行审查

本次修复：

- 补齐队长一次性建队时的循环 schema、提示和局部 ID 映射；普通任务不强制循环。状态工具和隔离流程讨论都能读取循环配置、轮次与暂停原因，环内任务讨论不再建议绕过门控重跑。
- AI 审核文件变化或不能完整读取时立即保存暂停原因，避免只返回工具错误后重复尝试。读取审核文件失败时不会先领取新执行令牌。门控负责人必须与配置的独立审核员一致，人工门控不分配执行成员。
- 修复跨轮刷新清空历史与固定比较记录；长历史在面板内部滚动。旧轮次的异步响应不会污染新一轮审核材料。
- 已完成任务在整环暂停后仍显示完成；环内禁用普通单节点重跑；AI 审核不会显示为人工验收。全局控制的并发版本包含循环状态，避免过期按钮操作。
- 画布尺寸包含回退连线与标签，回退线按整个循环区域计算留白，避免适应画布时裁掉下方回退线。

验证：完整验证链 36 个命令全部通过（526 个 Node 测试），随后补充的执行中暂停/同轮恢复用例也通过；循环专项现为 23 项。手动暂停撤销旧令牌，保留部分输出；上限续跑不会重置预算、丢失反馈或放行未通过的下游。人工/AI 两条 Edge 浏览器流程均通过，覆盖历史固定跨轮保留、长面板滚动、连线端点、中英文、深色与窄屏。打包产物通过真实 Harness `0.2.1-rc.5` 执行和冷启动场景。
